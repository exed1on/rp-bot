## 1. RMG Domain Primer

**Why it matters:** Showing you understand the domain instantly separates you from a generic backend candidate. The interviewer wants to know you grasp *why* this domain is hard.

**Core concepts:**
- **Player wallet** — the ledger of a player's money (real balance, bonus balance, locked/pending funds). Every game action touches it.
- **Bet lifecycle:** `place bet → debit wallet → game/round resolves → credit winnings (or not) → settle`. Each step must be atomic, idempotent, and auditable.
- **Real vs bonus balance** — bonuses have wagering requirements (e.g., "wager 30× before withdrawal"). Debits/credits must know which bucket they touch.
- **Regulatory reality:** licensed in 340+ jurisdictions (per the JD). Means: full **audit trails**, **responsible gaming** limits (deposit/loss/session limits), **transaction immutability**, reporting to regulators, KYC/AML. Data can't just be mutated — it must be traceable.
- **Idempotency everywhere** — networks retry. A retried "place bet" must NOT place two bets. A retried payout must NOT pay twice.
- **Consistency over availability for money** — in CAP terms, the wallet is a **CP** system. You'd rather reject a bet than double-spend. (Leaderboards, stats, etc. can be AP / eventually consistent.)

**One-liner to deliver:** *"In RMG the wallet is the heart of the system — it has to be strongly consistent, every operation idempotent, and every state change auditable, because mistakes here are regulatory and financial, not cosmetic."*

## 2. System Design: Player Wallet Service

This is the single most likely deep-design question. Here's a full worked answer you can rehearse.

### Step 1 — Requirements
**Functional:** deposit, withdraw, debit (place bet), credit (winnings), check balance, transaction history.
**Non-functional:** strong consistency (no double-spend), high availability, low latency (bets are real-time), idempotency, full audit trail, horizontal scalability.

### Step 2 — API
```
POST /wallets/{playerId}/transactions
  body: { type: DEBIT|CREDIT|DEPOSIT|WITHDRAW, amount, currency,
          idempotencyKey, reference (betId/roundId) }
GET  /wallets/{playerId}/balance
GET  /wallets/{playerId}/transactions?from=&to=
```
Every mutating call carries an **idempotencyKey** (usually a UUID generated by the caller per logical operation).

### Step 3 — Data model (the ledger pattern)
Don't store *just* a mutable balance. Use an **append-only ledger** (immutable transaction log) + a derived balance. This gives you auditability for free.

```
wallet(player_id PK, balance, version, currency, updated_at)
ledger_entry(id PK, player_id FK, type, amount, balance_after,
             idempotency_key UNIQUE, reference, created_at)
```

- `ledger_entry` is **append-only and immutable** — never updated or deleted. This is your audit trail and the regulator's source of truth.
- `idempotency_key UNIQUE` — the database enforces "process once." A retried request hits the unique constraint and you return the original result instead of re-applying.
- `wallet.balance` is a **materialized/cached projection** of the ledger for fast reads, protected by `version` for optimistic locking.

### Step 4 — The critical operation: a safe debit (place bet)
The race condition: two concurrent bets read balance=100, both think they can debit 80, both write → balance=20 but you let through 160 of bets. **Double-spend.**

**Fix — pick one, explain the trade-off:**

**(a) Pessimistic locking** — lock the row for the duration:
```sql
BEGIN;
SELECT balance FROM wallet WHERE player_id = ? FOR UPDATE;  -- locks row
-- check balance >= amount
UPDATE wallet SET balance = balance - ? WHERE player_id = ?;
INSERT INTO ledger_entry (...);  -- with idempotency_key
COMMIT;
```
Correct and simple. Cost: holds a lock → contention if one player spams bets. Fine because contention is *per-player* (one player rarely has massive parallelism).

**(b) Optimistic locking** — version check, retry on conflict:
```sql
UPDATE wallet SET balance = balance - ?, version = version + 1
WHERE player_id = ? AND version = ? AND balance >= ?;
-- if 0 rows updated → someone else won or insufficient funds → retry or reject
```
No lock held; better under low contention. Cost: must handle retries in app code.

**(c) Atomic conditional update** — push the check into the DB:
```sql
UPDATE wallet SET balance = balance - ?
WHERE player_id = ? AND balance >= ?;  -- 0 rows = insufficient funds, atomically
```

**What to say:** *"For a wallet I lean toward pessimistic locking or an atomic conditional update because correctness dominates throughput, and contention is naturally scoped per-player. I'd use the DB's ACID guarantees rather than coordinating in application code, and enforce idempotency with a unique constraint on the idempotency key."*

### Step 5 — Idempotency in detail
1. Request arrives with `idempotencyKey`.
2. Try to insert the ledger entry with that key inside the transaction.
3. **If unique-constraint violation** → this is a retry; load and return the original outcome (same response, same balance). Do NOT apply again.
4. This makes the whole operation **exactly-once** from the client's perspective even with at-least-once delivery.

### Step 6 — Scaling
- **Shard by playerId** — each player's wallet lives on one shard; no cross-player transactions in the common path, so sharding is clean.
- **Read replicas** for balance/history reads (accept slight staleness on history; balance reads that gate bets go to primary or use the cached `wallet.balance`).
- **Cache** hot balances in Redis (write-through, with the DB as source of truth).
- **Emit an event** (`WalletDebited`, `WalletCredited`) to Kafka after commit for downstream consumers (fraud, analytics, responsible-gaming limits) — see event-driven section.

### Step 7 — Trade-offs to name out loud
- SQL (PostgreSQL) over MongoDB **for the money** — you want ACID transactions and strong consistency.
- Strong consistency over availability — reject rather than risk double-spend.
- Ledger/event-sourced model over mutable balance — auditability and the ability to rebuild balance from history.

## 3. System Design: Bet Placement at Scale

**Flow:** `Bet Service → Wallet Service (debit) → Game Engine (resolve) → Wallet Service (credit if win) → Settlement`.

**Key challenges & answers:**
- **Distributed transaction across services** — you can't use one DB transaction across Wallet + Bet + Game. Use the **Saga pattern** (section 7): place bet = debit wallet; if game fails, **compensate** by crediting back.
- **Exactly-once** — idempotency keys on every step + idempotent consumers on Kafka.
- **Ordering** — events for one player/bet must stay ordered → Kafka partition key = `playerId` (or `betId`).
- **Latency** — bet placement is user-facing real-time. Keep the synchronous path short (debit + accept), resolve asynchronously, push result via event/WebSocket.
- **Throughput** — partition by player; scale consumers horizontally within a consumer group.

**Pattern to articulate:** *"I'd keep the synchronous critical path minimal — validate and debit atomically, return fast — and handle resolution and downstream effects asynchronously through events, using a saga with compensating transactions to keep the wallet and bet state consistent without a distributed 2-phase commit."*

## 4. Consistency, Transactions & Locking

### ACID (be able to give a money example for each)
- **Atomicity** — debit + ledger insert both happen or neither (no money vanishes).
- **Consistency** — constraints hold (balance never negative).
- **Isolation** — concurrent bets don't corrupt each other.
- **Durability** — a committed deposit survives a crash.

### Isolation levels & anomalies (know which anomaly each prevents)
| Level | Dirty read | Non-repeatable read | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | ✅ possible | ✅ | ✅ |
| READ COMMITTED | ❌ | ✅ | ✅ |
| REPEATABLE READ | ❌ | ❌ | ✅ (✅ prevented in MySQL InnoDB via gap locks) |
| SERIALIZABLE | ❌ | ❌ | ❌ |

- **Dirty read:** reading uncommitted data that may roll back.
- **Non-repeatable read:** same row read twice gives different values (another tx updated it).
- **Phantom:** same query returns different *rows* (another tx inserted).
- For a wallet, READ COMMITTED + explicit row locking (`FOR UPDATE`) is the common, pragmatic choice; SERIALIZABLE is safest but costs throughput.

### Optimistic vs Pessimistic locking
- **Pessimistic** (`SELECT ... FOR UPDATE`): assume conflict, lock first. Good for **high-contention** + short transactions. Risk: deadlocks, reduced concurrency.
- **Optimistic** (version column, check-on-write): assume no conflict, detect on commit, retry. Good for **low-contention**. Risk: wasted work on retry under contention.
- **Rule of thumb to state:** *"High contention or a must-not-fail critical section → pessimistic. Low contention, read-heavy → optimistic with a version column."*

### Distributed locking (when one DB isn't enough)
- Use **Redis** (`SET key value NX PX 30000` — set-if-not-exists with expiry) or **Redlock** for multi-node.
- **Caveat to mention:** distributed locks are best-effort; for true correctness prefer a single source of truth with DB transactions/idempotency. Locks help coordination, not guarantee.

## 5. Concurrency: Hard Scenarios & Idempotency

**Scenario the interviewer loves:** *"Two threads update a player's balance simultaneously. Walk me through everything that can go wrong and how you'd fix each."*

**Failure modes:**
1. **Lost update** — both read 100, both write 100−X; one update is lost. → Fix: atomic update / locking / version check.
2. **Read-modify-write race** — `balance = balance - amount` in app code is three steps. → Fix: do it in one SQL statement or under a lock.
3. **Double-processing on retry** — client retries a timed-out request; bet applied twice. → Fix: idempotency key + unique constraint.
4. **Check-then-act** — check balance ≥ amount, then debit; balance changed in between. → Fix: combine into one atomic conditional `UPDATE ... WHERE balance >= amount`.

**Java-level concurrency (if it goes in-process):**
- `synchronized` / `ReentrantLock` only help *within one JVM* — useless across service instances. Say this explicitly; it shows you understand distributed reality.
- `AtomicInteger`/CAS for in-memory counters; `compareAndSet` is lock-free optimistic concurrency.
- `ConcurrentHashMap` for shared in-memory state; understand it uses CAS + per-bin locking.
- For cross-instance correctness, push the invariant down to the **database** (single source of truth) or a **distributed lock** — not JVM locks.

**Idempotency patterns (have these ready):**
- **Idempotency key + unique constraint** (the gold standard for money).
- **Dedup table / processed-message log** for Kafka consumers (store processed message IDs).
- **Natural idempotency** — design operations to be safe to repeat (e.g., "set status = SETTLED" is idempotent; "add 10" is not).

## 6. Event-Driven Architecture & Kafka

**Why event-driven for gaming:** decoupling (wallet doesn't need to know about analytics), scalability (consumers scale independently), **auditability/replay** (events are a log you can replay), resilience (a down consumer doesn't block producers).

### Kafka fundamentals (be precise)
- **Topic** → split into **partitions** (the unit of parallelism and ordering).
- **Ordering is guaranteed only *within* a partition**, not across. → To keep one player's events ordered, use **`playerId` as the partition key** so they all land in the same partition.
- **Offset** — each message's position in a partition; consumers commit offsets to track progress.
- **Consumer group** — consumers in a group split partitions among themselves (parallelism). Each partition is consumed by exactly one consumer in the group. More consumers than partitions = idle consumers.
- **Retention** — Kafka keeps messages for a configured time/size regardless of consumption → enables **replay** (huge for audit and rebuilding state).

### Delivery semantics (know the trade-offs)
- **At-most-once** — commit offset before processing; crash = message lost. Rarely acceptable for money.
- **At-least-once** (default, common) — process then commit; crash between = reprocessing → **consumers must be idempotent.**
- **Exactly-once (EOS)** — Kafka transactions + idempotent producer (producer IDs + sequence numbers) + `read_process_write` in a transaction. Powerful but costly/complex; often people use **at-least-once + idempotent consumers** to get effectively-once more cheaply.

**Key line:** *"I default to at-least-once delivery with idempotent consumers — it's simpler and cheaper than full exactly-once, and idempotency keys give me effectively-once semantics where it matters, like the wallet."*

### Reliability patterns
- **Dead Letter Queue (DLQ)** — messages that repeatedly fail go to a DLQ for inspection instead of blocking the partition.
- **Idempotent consumer** — track processed message IDs (dedup table) so reprocessing is safe.
- **Schema registry / Avro** — enforce message schema compatibility across producers/consumers.
- **Backpressure / consumer lag** — monitor lag; scale consumers; partition adequately.

### Kafka vs RabbitMQ (one-liner)
*"RabbitMQ is a smart broker with rich routing, push-based, deletes after ack — great for complex routing and task queues. Kafka is a distributed log, pull-based, retains messages for replay, scales to very high throughput — great for event streaming, audit, and event sourcing. For an event-driven RMG platform with audit and replay needs, Kafka fits the backbone."*

## 7. Saga Pattern (Distributed Transactions)

**Problem:** A bet spans Wallet, Bet, and Game services — each with its own DB. You can't wrap them in one ACID transaction, and **2-phase commit (2PC) doesn't scale and creates tight coupling/blocking.**

**Solution:** A **saga** = a sequence of local transactions, each publishing an event that triggers the next. If a step fails, run **compensating transactions** to undo prior steps.

**Example — place bet saga:**
1. Wallet: debit balance → emit `WalletDebited`
2. Bet: create bet record → emit `BetPlaced`
3. Game: run round → emit `RoundResolved`
4. Wallet: credit winnings (if win) → `WalletCredited`
- **If Game fails after debit:** compensating tx → Wallet credits the amount back (`WalletRefunded`). The bet is marked failed.

**Two styles (know both + the trade-off):**
- **Choreography** — services react to each other's events, no central coordinator. Decentralized, loosely coupled; but hard to follow the flow / debug as it grows.
- **Orchestration** — a central **saga orchestrator** tells each service what to do and tracks state. Easier to reason about, visualize, and handle failures; but the orchestrator is a component to maintain.

**Key line:** *"For complex flows with many steps and compensations I prefer orchestration — it centralizes the state machine and makes failure handling explicit. For simple 2–3 step flows, choreography is lighter. Either way, compensating transactions replace rollback, and every step is idempotent."*

**Note:** Compensation is *semantic* undo, not a DB rollback — you credit money back, you don't erase history. The refund is itself a ledger entry (auditability preserved).

## 8. Event Sourcing & CQRS

(Aristocrat's .NET stack explicitly uses CQRS — worth knowing well.)

### Event Sourcing
- Instead of storing current state, store the **sequence of events** that produced it. Current state = fold/replay events.
- Wallet example: instead of `balance = 120`, store `Deposited(100), BetDebited(50), WonCredited(70)` → replay → 120.
- **Benefits:** complete audit trail (perfect for RMG/regulators), time-travel/debugging, rebuild state, natural fit with Kafka.
- **Costs:** more complex, eventual consistency on read side, event schema evolution, replay cost (mitigated by **snapshots**).

### CQRS (Command Query Responsibility Segregation)
- **Separate the write model from the read model.** Commands (mutations) go through one path; queries (reads) use separate, optimized read models (projections).
- Pairs naturally with event sourcing: writes append events; **projections** build query-optimized views (e.g., a denormalized balance table, a transaction-history view) from those events.
- **Benefits:** independent scaling of reads vs writes, optimized read models, clean separation.
- **Costs:** complexity, eventual consistency between write and read sides (a write may not instantly appear in reads).

**When to use / not:** Great for complex domains with heavy audit and asymmetric read/write loads (RMG fits). Overkill for simple CRUD. **Say that** — knowing when *not* to use a pattern signals maturity.

## 9. Redis Deep Dive

**Why it's in the stack:** in-memory, sub-millisecond, versatile. In gaming it's used a lot.

**Data structures & gaming uses:**
- **Strings** — cache, counters (`INCR`).
- **Hashes** — store objects (player session, wallet snapshot).
- **Sorted Sets (ZSET)** — **leaderboards** (score-ordered, `ZADD`/`ZRANGE`) — the canonical gaming use case.
- **Sets** — unique tracking (online players).
- **Lists** — simple queues.
- **Streams** — lightweight event streaming / message queue.

**Key patterns:**
- **Caching (cache-aside):** app checks Redis → miss → load from DB → populate Redis. Most common.
- **Write-through:** write to Redis + DB together (fresh, slower writes). Keep DB as source of truth.
- **Distributed lock:** `SET lock:resource token NX PX 30000` (set-if-absent + auto-expiry so a crashed holder doesn't deadlock forever). Release by checking the token (use a Lua script to make check-and-delete atomic). For multi-node, **Redlock** — but mention its correctness debate; for money, prefer DB invariants.
- **Rate limiting:** `INCR` a per-key counter with a TTL (fixed window), or sorted-set sliding window. Used for API throttling, responsible-gaming limits.
- **Session storage:** stateless services + shared sessions in Redis.

**Eviction & persistence:**
- Eviction policies: `noeviction`, `allkeys-lru`, `volatile-lru`, `allkeys-lfu`, etc. **LRU** most common for caches.
- Persistence: **RDB** (point-in-time snapshots) and **AOF** (append-only log of writes). Trade durability vs performance.
- Single-threaded command execution → commands are atomic; use **Lua scripts** or `MULTI/EXEC` for multi-step atomicity.

**Cache consistency caveat to mention:** cache invalidation is hard; with a wallet you'd treat the DB as truth and either write-through or invalidate-on-write, accepting that the cached balance is a fast-path optimization, not the authority.

## 10. Reactive Programming in Java

(One of the two gaps the first interviewer flagged. You don't need production experience — you need to *understand the model and articulate when it helps.*)

**The core idea:** Non-blocking, asynchronous, event-driven processing of data streams with **backpressure**. Instead of thread-per-request (blocking on I/O), a small number of event-loop threads handle many concurrent requests, never blocking.

**Why it matters:** Traditional thread-per-request: 10,000 concurrent slow I/O calls = 10,000 blocked threads = memory + context-switching death. Reactive: those threads aren't blocked waiting on I/O, so a few threads serve thousands of concurrent connections. **Best for high-concurrency, I/O-bound workloads** (lots of network/DB calls, streaming, many simultaneous users).

**Project Reactor (Spring WebFlux's library):**
- **`Mono<T>`** — 0 or 1 element (e.g., one HTTP response).
- **`Flux<T>`** — 0..N elements (a stream).
- **Lazy** — nothing happens until you `subscribe()`. The pipeline describes *what* to do; subscription triggers it.
- **Operators:** `map`, `flatMap`, `filter`, `zip`, `merge` — compose async pipelines declaratively.
- **Schedulers** — control which threads work runs on (`subscribeOn`, `publishOn`).

**Backpressure:** the consumer signals how much it can handle so a fast producer doesn't overwhelm a slow consumer. This is the defining feature vs plain async — flow control is built in (`request(n)` in the Reactive Streams spec: Publisher/Subscriber/Subscription/Processor).

**Spring WebFlux vs Spring MVC:**
- MVC = blocking, servlet, thread-per-request, simple, mature.
- WebFlux = non-blocking, reactive, Netty/event-loop, scales for high-concurrency I/O.
- **Caveat:** reactive only pays off if the *whole chain* is non-blocking (reactive DB driver like R2DBC or reactive Mongo). One blocking call poisons the event loop. Don't go reactive just because it's trendy — it adds cognitive complexity and is harder to debug.

**How to answer the gap honestly:** *"I haven't shipped WebFlux to production, but I understand the model — non-blocking event loops, Mono/Flux, and backpressure via the Reactive Streams spec. It shines for high-concurrency I/O-bound services where thread-per-request would exhaust threads, as long as the entire call chain stays non-blocking. Given my track record I'd ramp on it quickly."* Confidence + understanding + ramp-speed. No apology.

## 11. MongoDB

(The other flagged gap. Same approach: understand the model and the *when*.)

**What it is:** a document database — stores **BSON** (binary JSON) documents in collections. Schema-flexible (documents in a collection can differ).

**Document model vs relational:**
- Relational: normalized tables, joins, rows.
- Mongo: denormalized documents; **embed related data** that's read together (e.g., a game config with its nested rules) to avoid joins. Reference (store IDs) when data is shared or grows unbounded.

**When to use Mongo vs SQL (the key interview judgment):**
- **Mongo:** flexible/evolving schema, document-shaped data read as a unit, high write throughput, horizontal scale, content/catalog/config, player profiles, game metadata.
- **SQL (PostgreSQL):** **money, transactions, strong relational integrity** — anything needing ACID across multiple rows/entities. **The wallet stays in SQL.**
- **The line to deliver:** *"I'd use PostgreSQL for the wallet and anything financial because I want ACID and strong consistency, and MongoDB for flexible, document-shaped data like game content, configs, or player profiles where the schema evolves and reads are document-oriented."*

**Key mechanics:**
- **Indexes** — single-field, compound, etc.; without them queries do collection scans (same idea as SQL). Index your query and sort fields.
- **Sharding** — horizontal scale across nodes by a **shard key**; choose a high-cardinality, evenly-distributed key to avoid hot shards.
- **Replica sets** — primary + secondaries for HA and read scaling; automatic failover via election.
- **Transactions** — Mongo *does* support multi-document ACID transactions (since 4.0), but they're more costly and less natural than in a relational DB — another reason money lives in SQL.
- **Consistency** — tunable read/write concerns (e.g., `majority` write concern for durability across replicas).
- **Aggregation pipeline** — `$match`, `$group`, `$lookup` (joins) for analytics-style queries.

## 13. Mock Round-2 Q&A

Rehearse answering these out loud.

**Q: Design a system to handle player bets with a wallet. How do you prevent double-spending?**
→ Wallet service with append-only ledger + idempotency keys; atomic conditional update or `SELECT FOR UPDATE`; strong consistency (PostgreSQL); emit events to Kafka post-commit; saga for cross-service consistency. (See §2.)

**Q: A bet request times out and the client retries. How do you guarantee it's not placed twice?**
→ Idempotency key generated per logical operation; unique constraint on the ledger; on retry, the constraint blocks re-application and you return the original result. Effectively-once. (See §5.)

**Q: How do you keep one player's events in order through Kafka?**
→ Partition by `playerId`; ordering is guaranteed within a partition. (See §6.)

**Q: At-least-once vs exactly-once — what do you use and why?**
→ At-least-once + idempotent consumers for simplicity/cost; full EOS only where justified. (See §6.)

**Q: How do two services agree on a transaction without a distributed transaction?**
→ Saga with compensating transactions; orchestration for complex flows; every step idempotent; no 2PC. (See §7.)

**Q: Where would you use Redis here?**
→ Cache hot balances (DB is truth), leaderboards (sorted sets), rate limiting / responsible-gaming limits, distributed locks (with caveats), session storage. (See §9.)

**Q: Two threads update the same balance — what breaks?**
→ Lost update, read-modify-write race, check-then-act, double-processing; fix each with atomic updates / locking / version columns / idempotency. JVM locks don't help across instances — push the invariant to the DB. (See §5.)

**Q: When would you choose Mongo over Postgres?**
→ Flexible document data (game content/config, profiles) → Mongo; money/transactions → Postgres. (See §11.)

**Q: You don't have Reactive experience — talk me through it anyway.**
→ Non-blocking event loop, Mono/Flux, backpressure via Reactive Streams; great for high-concurrency I/O if the whole chain is non-blocking; I'd ramp fast. (See §10.)

**Q: How do you use AI tools responsibly in this codebase?**
→ Draft-not-truth, always review/test/validate, security-conscious, human keeps architectural judgment. (See §12.)

**Q: How do you make the wallet auditable for regulators?**
→ Append-only immutable ledger / event sourcing; every state change is a recorded entry; nothing is mutated or deleted; replayable history. (See §2, §8.)

## 14. Cheat Sheets & Talking Points

**Phrases that signal seniority (use them naturally):**
- "Correctness dominates throughput here, so I'd lean pessimistic / use the DB's ACID guarantees."
- "I'd make this idempotent with a key and a unique constraint, so retries are safe."
- "JVM locks only help within one instance — for cross-instance correctness I push the invariant to the database."
- "I'd keep the synchronous path minimal and handle the rest asynchronously via events."
- "Compensating transactions, not rollback — and the compensation is itself an audited ledger entry."
- "I'd reach for this pattern *only when* the complexity is justified — for simple CRUD it's overkill." (knowing when *not* to)
- "Everything financial stays in Postgres for ACID; flexible document data goes to Mongo."

**Decision quick-reference:**
| Need | Choice |
|---|---|
| Money / transactions | PostgreSQL, ACID, strong consistency |
| Flexible document data | MongoDB |
| Hot reads / leaderboards / locks / rate limits | Redis |
| Event backbone / audit / replay | Kafka |
